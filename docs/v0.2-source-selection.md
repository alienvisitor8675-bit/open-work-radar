## Real-data actionability checks

The production review supports the hardening added in PR #16:

- **Lifecycle / active work:** HHS/simpler-grants-gov#9814 had an active submitted PR and later closed. It is not treated as available work merely because its issue body still contains bounty text.
- **Ambiguous availability:** cxlinux-ai/cx-distro#34 is open and advertises a `$25 upon merge` bounty, but recent non-maintainer comments repeatedly ask whether it is still available and no newer maintainer confirmation is visible. It is withheld rather than assumed actionable.
- **Funding pending:** 0xSachinK/openplaid#17 still explicitly says `NOT FUNDED`, carries a `funding-pending` label, and instructs contributors not to start paid work until funding is confirmed. It is withheld.
- **Search-window / direct revalidation:** retained candidates that disappear from the bounded two-page search window are directly revalidated before being kept or removed. The production dataset stayed small after the hardening cutover instead of accumulating search-window ghosts.
- **Multi-claim behavior:** legitimate multi-claim bounty rows such as Scottcjn/rustchain-bounties remain eligible when there is no actual attached open work PR; claim-like comments alone do not suppress them.

The review also found two new narrow false-positive shapes:

1. `Build-to-earn scan ...` roundup Issues that contain prize amounts for external opportunities.
2. `Internal test bounty ...` incident/bug Issues that describe a bounty-system failure and mention escrow/reward amounts but are not work offers themselves.

Issue #17's branch adds title-shaped regression guards for those observed cases rather than excluding broad categories such as all `bug` Issues.

## Algora vs Opire

### Algora

Primary references:

- API reference: https://api.docs.algora.io/
- Example public bounty board: https://algora.io/projectdiscovery/bounties
- Open bounty example: https://algora.io/spaceandtimelabs/bounties?status=open

Observations:

- Algora publishes an official API reference covering **Bounties, Claims, Tasks, Solvers, Issues, and Pull Requests**.
- The public bounty UI exposes explicit open/completed state, reward amount, linked repository/issue, and claim counts.
- Claims and pull-request entities are first-class concepts, which is a strong fit for Open Work Radar's actionability model and later competition/lifecycle enrichment.
- Algora's public open-source repository is active, but its currently visible legacy tRPC bounty route is not sufficient evidence by itself for the production API contract; adapter implementation should follow the official API reference rather than internal legacy routes.

Risk/unknowns to verify in the adapter Issue:

- exact public read endpoint and pagination contract;
- authentication requirements for read-only discovery;
- rate-limit and retry behavior;
- stable identifiers for deduplication against GitHub-discovered rows.

### Opire

Primary references:

- Getting started: https://docs.opire.dev/overview/getting-started
- Commands: https://docs.opire.dev/overview/commands
- Lifecycle: https://docs.opire.dev/rewards/lifecycle
- Costs and payments: https://docs.opire.dev/rewards/pricing

Additional implementation evidence:

- Community watcher using the public endpoint: https://github.com/SergeySolovyev/opire-watcher

Observations:

- Opire's official docs define a clean lifecycle: create bounty, `/try`, PR, `/claim`, creator review, payment arrangement.
- The docs explicitly support multiple bounties per issue and expose a useful distinction between trying and claiming.
- A community watcher successfully consumes `https://api.opire.dev/rewards?page=1&itemsPerPage=100` and observes structured reward amount, repository/project links, programming languages, claimer users, trying users, and creation time.
- However, the public REST discovery endpoint is not currently documented in the official docs used for this review. Community snapshots have also shown rewards whose backing GitHub Issues were already closed, so GitHub-side lifecycle revalidation would remain mandatory.

## Decision

**Select Algora as the first external source for v0.2.**

Why:

1. It has the stronger first-party machine-readable contract: an official API reference explicitly covers the entities Open Work Radar needs.
2. It exposes richer actionability evidence than a reward list alone, especially claims and pull-request relationships.
3. The public product currently shows concrete open bounty state and claim counts, making it suitable for conservative cross-validation.
4. It fits the existing normalized model without requiring Open Work Radar to trust platform state blindly: GitHub issue/PR state can still be revalidated before an opportunity is emitted.

**Opire remains the preferred second external-source candidate.** Its public reward feed appears straightforward to integrate, but the discovery API needs first-party contract verification before it should outrank Algora.

## v0.2 implementation boundary

The first Algora adapter should be a separate focused change. It should:

- use the official API contract, not scrape HTML;
- ingest only records with enough source evidence to resolve a GitHub issue/repository;
- normalize reward, source URL, platform status, and competition/claim signals where available;
- deduplicate against GitHub-discovered opportunities by canonical GitHub issue URL when possible;
- revalidate GitHub issue state and active-work signals before marking an Algora record actionable;
- preserve the current once-daily schedule initially;
- fail conservatively on API/auth/schema uncertainty, leaving existing GitHub data intact.
