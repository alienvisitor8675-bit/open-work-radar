## Real-data actionability checks

The production review supports the hardening added in PR #16:

- **Lifecycle / active work:** HHS/simpler-grants-gov#9814 had an active submitted PR and later closed. It is not treated as available work merely because its issue body still contains bounty text.
- **Ambiguous availability:** cxlinux-ai/cx-distro#34 is open and advertises a `$25 upon merge` bounty, but recent non-maintainer comments repeatedly ask whether it is still available and no newer maintainer confirmation is visible. It is withheld rather than assumed actionable.
- **Funding pending:** 0xSachinK/openplaid#17 still explicitly says `NOT FUNDED`, carries a `funding-pending` label, and instructs contributors not to start paid work until funding is confirmed. It is withheld.
- **Search-window / direct revalidation:** retained candidates that disappear from the bounded two-page search window are directly revalidated before being kept or removed. The production dataset stayed small after the hardening cutover instead of accumulating search-window ghosts.
- **Multi-claim behavior:** legitimate multi-claim bounty rows remain eligible when there is no actual attached open work PR; claim-like comments alone do not suppress them.

The review also found two narrow false-positive shapes that are covered by regression tests:

1. `Build-to-earn scan ...` roundup Issues that contain prize amounts for external opportunities.
2. `Internal test bounty ...` incident/bug Issues that describe a bounty-system failure and mention escrow/reward amounts but are not work offers themselves.

## Algora vs Opire: initial review

### Algora

References:

- API reference: https://api.docs.algora.io/
- Public implementation: https://github.com/algora-io/algora
- Terms: https://algora.io/legal/terms

The initial Issue #17 review preferred Algora because its official API reference described Bounties, Claims, Tasks, Solvers, Issues, and Pull Requests. Those concepts were an excellent fit for Open Work Radar's lifecycle model.

### Opire

References:

- Getting started: https://docs.opire.dev/overview/getting-started
- Commands: https://docs.opire.dev/overview/commands
- Lifecycle: https://docs.opire.dev/rewards/lifecycle
- Costs and payments: https://docs.opire.dev/rewards/pricing
- Terms: https://opire.dev/terms-of-service
- Community endpoint consumer: https://github.com/SergeySolovyev/opire-watcher

Opire's official docs define a clear lifecycle around creating rewards, `/try`, pull requests, `/claim`, creator review, and payment arrangement. They also explicitly support multiple rewards on one Issue.

A community watcher and other independent open-source consumers use the public JSON endpoint:

```text
GET https://api.opire.dev/rewards?page=1&itemsPerPage=100
```

Observed fields include reward ID, `pendingPrice`, GitHub Issue URL, project metadata, programming languages, claimer users, trying users, and creation time. `pendingPrice.unit == "USD_CENT"` is converted from cents to USD by those consumers.

The endpoint is **not documented in the official Opire docs reviewed for this change**, so it must be treated as provisional rather than as a stable first-party API contract.

## Implementation-gate correction in Issue #18

The Issue #18 acceptance gate required checking the live Algora contract again before writing the adapter. That check changed the source decision.

Current published Algora application code routes `/api/trpc/bounty.list` under a section explicitly marked as legacy. Its current bounty controller renders an empty bounty list, with the former filtering implementation commented out. No usable current read-only bounty discovery endpoint was verified from the published application implementation.

Falling back to periodic HTML collection is also not acceptable: Algora's current Terms prohibit using a robot, spider, or other automatic process to access the Service for monitoring/copying material. Open Work Radar's design explicitly requires respecting platform automation constraints.

Therefore:

- **Algora is deferred** until an explicitly supported machine-readable discovery API or suitable permission can be verified.
- **Opire becomes the first external-source pilot for v0.2.**

This is a correction to the initial Issue #17 choice, not evidence that Algora is unsuitable in general. The blocker is the currently verifiable automation/API contract.

## Opire v0.2 contract and safety boundary

The first Opire adapter intentionally treats the public rewards endpoint as provisional:

- use bounded pagination with a descriptive user-agent;
- reject non-list/unknown response shapes;
- accept only records that resolve to canonical `github.com/<owner>/<repo>/issues/<number>` URLs;
- accept positive `USD` / `USD_CENT` values only; unknown currency units are not guessed;
- revalidate backing GitHub Issue state before emitting an opportunity;
- reuse GitHub lifecycle checks for assignees, deadlines, active work PRs, ambiguous availability, and explicit not-actionable/funding-pending signals;
- store only aggregate `trying` / `claimer` counts, never Opire usernames or user IDs;
- do not suppress a multi-claim opportunity solely because try/claim counts are non-zero;
- if multiple Opire reward records map to one GitHub Issue, display the largest single pending amount instead of summing until aggregation semantics are documented;
- merge GitHub + Opire discoveries by canonical GitHub Issue URL and preserve both source provenances;
- if the Opire feed fails or its schema becomes uncertain, preserve the last known Opire rows while continuing a successful GitHub refresh;
- if GitHub lifecycle revalidation for one Opire row fails, preserve that previous row rather than interpreting missing evidence as closure;
- never treat a platform listing as a guaranteed payout.

The scheduled cadence remains once per day at `17 0 * * *` (00:17 UTC). Source coverage is being expanded; scan frequency is not.
